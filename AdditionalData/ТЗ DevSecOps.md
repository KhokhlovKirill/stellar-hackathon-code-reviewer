# **Техническое задание: DevSecOps AI-бот для автоматического ревью Pull Request**

---

## **1\. Общее описание сервиса**

Сервис представляет собой AI-агента, который автоматически анализирует каждый новый Pull Request (PR) или Merge Request (MR) в репозитории на GitHub или GitLab. Бот подключается через вебхуки, получает diff изменений, прогоняет его через набор статических анализаторов и LLM, после чего публикует inline-комментарии прямо в интерфейсе репозитория. При обнаружении критических уязвимостей бот блокирует слияние. Разработчик может вести диалог с ботом прямо в комментариях.

Целевая аудитория — разработчики и DevSecOps-команды, которые хотят автоматизировать проверку безопасности кода без ручного ревью на каждом PR.

---

## **2\. Технологический стек**

**Backend:** Python, FastAPI (async, нативная обработка вебхуков)

**LLM:** Anthropic Claude API (claude-sonnet) — приоритет, как запасной вариант OpenAI GPT-4

**Базы данных:** PostgreSQL (аудит-лог всех анализов и диалогов) \+ Redis (кеш диффов, сессии диалога с ботом)

**Очереди задач:** Celery \+ Redis (параллельный анализ нескольких PR одновременно)

**Статический анализ:** Semgrep (SAST \+ AI-правила), Bandit (Python), интеграция с OSV API (Open Source Vulnerabilities)

**Сканер секретов:** TruffleHog или Gitleaks (локально, до отправки кода в LLM)

**Зависимости:** PyPI JSON API \+ OSV API для проверки CVE

**Инфраструктура:** Docker Compose для локального запуска и демо, возможность деплоя на VDS (Ubuntu 24.04)

**Frontend:** React \+ TypeScript, Tailwind CSS

**API между фронтом и бэком:** REST

---

## **3\. Архитектура системы**

Поток данных выглядит следующим образом:

1. Разработчик открывает PR в GitHub/GitLab  
2. Git-провайдер отправляет вебхук на FastAPI-сервер  
3. Сервер ставит задачу в очередь Celery  
4. Worker извлекает diff PR через API провайдера  
5. Diff фильтруется (отсекаются .md, .lock, картинки, локали)  
6. Локальный сканер секретов (TruffleHog/Gitleaks) проверяет diff до отправки во внешний API  
7. Semgrep/Bandit прогоняют статический анализ  
8. Зависимости (requirements.txt, package.json) проверяются через OSV API  
9. Diff \+ контекст ±50 строк вокруг каждого чанка \+ результаты статанализа передаются в LLM  
10. LLM возвращает JSON с находками  
11. Бот публикует inline-комментарии в PR и при необходимости блокирует merge  
12. Все события логируются в PostgreSQL

Абстракция провайдеров реализована через базовый класс GitProvider с наследниками GitHubProvider и GitLabProvider. Это позволяет легко добавить Bitbucket или любой другой провайдер.

## **4\. Backend: функциональные требования**

### **4.1 Webhook-сервер**

* Приём вебхуков от GitHub (события: pull\_request opened/updated/synchronized, issue\_comment created) и GitLab (merge\_request, note)  
* Верификация подписи вебхука (HMAC-SHA256)  
* Немедленный ответ 200 OK, постановка задачи в очередь  
* Фильтрация событий: пропускать только PR/MR с изменениями кода

### **4.2 Парсер диффов**

* Получение patch/diff через API провайдера  
* Фильтрация нерелевантных файлов: .md, .gitignore, .lock, картинки, локализационные файлы  
* Разбивка на чанки по файлам и функциям  
* Запрос ±50 строк контекста вокруг каждого изменённого чанка через API репозитория (Smart Context Window)  
* Парсинг AST для Python/JavaScript, чтобы подтянуть тела вызываемых функций из других файлов (Code RAG)

### **4.3 Локальный пре-анализ (до LLM)**

* Запуск TruffleHog или Gitleaks на diff — поиск секретов до отправки во внешний API  
* Энтропийный анализ Шеннона для строк с присвоениями переменных: высокая энтропия \= вероятный токен/ключ, который не поймают regex  
* Запуск Semgrep с набором правил OWASP  
* Для Python дополнительно Bandit  
* Парсинг файлов зависимостей (requirements.txt, Pipfile, package.json) из diff и проверка версий через OSV API и PyPI JSON API

### **4.4 LLM-модуль**

Системный промпт жёстко задан в следующем формате:

You are a security code reviewer. Analyze ONLY the provided git diff.

RULES:  
\- Report ONLY confirmed vulnerabilities, never speculation  
\- For each finding: severity (critical/high/medium/low), CWE ID, affected line, explanation, fix snippet  
\- If no vulnerabilities found, respond: {"findings": \[\]}  
\- Do NOT flag: test files with mock data, commented-out code, documentation

CONTEXT: {language}, {framework}, {file\_path}  
DIFF:  
{diff\_chunk}

Respond ONLY in JSON. No markdown, no preamble.

LLM возвращает строго JSON. Парсинг автоматический. В промпт передаётся язык, фреймворк, путь к файлу, diff-чанк и результаты статанализа как дополнительный контекст.

### **4.5 Risk Score**

Каждый PR получает числовой Risk Score от 0 до 100 с breakdown по типам:

* SQL-инъекция: \+40  
* Hardcoded secret: \+35  
* Устаревшая уязвимая зависимость: \+15  
* XSS: \+30  
* Прочие medium/low: \+5–10 каждое

Итоговый скор определяет цвет метки в комментарии: зелёный (0–30), жёлтый (31–60), красный (61–100).

### **4.6 Публикация результатов**

* Inline-комментарии к конкретным строкам кода через API провайдера  
* Общий Summary-комментарий в начале PR: Risk Score, количество находок по уровням, список файлов  
* При Risk Score \> 60 или наличии critical-находок: автоматическая блокировка merge через API (decline/block)  
* Mermaid.js диаграмма "Blast Radius" в комментарии: какие внутренние модули используют уязвимую библиотеку

### **4.7 Автоматический PR с фиксом**

Если найден hardcoded secret — бот создаёт новый PR: секрет переносится в .env, добавляется пример в .env.example. Если найдена уязвимая зависимость — бот создаёт PR с обновлённой версией до patched.

### **4.8 Диалоговый режим (ChatOps)**

* Бот обрабатывает комментарии вида @secbot \<команда\>  
* Поддерживаемые команды:  
  * @secbot why is this SQL injection? — объясняет механизм, показывает PoC-эксплойт (curl-запрос или Python-скрипт), предлагает исправленный сниппет  
  * @secbot explain how this XSS works — аналогично для XSS  
  * @secbot false positive, this is test data — бот фиксирует исключение в PostgreSQL  
  * @secbot ignore, /tests/ directory — добавляет паттерн в team-specific исключения  
  * @secbot scan full — запускает retro-анализ всего репозитория  
* Сессия диалога хранится в Redis, контекст предыдущих сообщений передаётся в LLM при каждом ответе

### **4.9 Retro-анализ репозитория**

По команде @secbot scan full или через веб\-интерфейс:

* Бот клонирует или обходит репозиторий через API  
* Прогоняет все файлы через ту же логику, что и для новых PR  
* Генерирует Summary Report в виде markdown-файла и коммитит его в репозиторий (или прикрепляет к Issues)  
* Отображает результаты в веб\-панели

### **4.10 Обучение на False Positives**

* Все отметки @secbot false positive сохраняются в PostgreSQL с привязкой к паттерну кода и директории  
* После 3+ отметок одного и того же паттерна он автоматически добавляется в team-specific исключения промпта  
* Исключения применяются к следующим анализам этой команды/организации

### **4.11 Security Knowledge Base (векторная БД)**

* Каждая найденная и исправленная уязвимость классифицируется по типу (CWE) и сохраняется в векторную БД (например, pgvector или Chroma)  
* При новых анализах бот ищет похожие паттерны и может написать в комментарии: "Похожая проблема уже решалась в PR \#142"

### **4.12 Логирование и аудит**

* Все события записываются в PostgreSQL: вебхук получен, diff извлечён, статанализ запущен, LLM запрошен, комментарий опубликован  
* Полный лог запросов/ответов LLM для аудита  
* JSON-формат логов для удобного парсинга и визуализации

## **5\. Frontend: функциональные требования**

### **5.1 Общая структура**

Веб-интерфейс — административная панель и дашборд для менеджеров/тимлидов. Разработчики взаимодействуют через интерфейс GitHub/GitLab, но веб\-панель даёт общую картину по всем PR.

Страницы приложения:

* Dashboard (главная)  
* Репозитории (список подключённых)  
* PR-аналитика  
* Настройки  
* Knowledge Base

### **5.2 Dashboard**

* Сводная статистика: всего PR проанализировано, заблокировано merge, найдено уязвимостей за последние 7/30 дней  
* График динамики находок по типам за период (линейный, recharts или аналог)  
* График Risk Score по PR во времени  
* Список последних проанализированных PR с Risk Score, статусом (pass / blocked) и ссылкой на PR  
* Цветовая индикация: красный / жёлтый / зелёный

### **5.3 Страница репозитория**

* Карточка репозитория: название, провайдер (GitHub/GitLab), статус вебхука (активен / ошибка)  
* Кнопка "Запустить retro-анализ" — запускает @secbot scan full через UI  
* История анализов репозитория: список PR с датой, Risk Score, количеством находок  
* Настройки для репозитория: порог блокировки merge (по умолчанию 60), список игнорируемых директорий, активные правила Semgrep

### **5.4 Страница анализа конкретного PR**

* Заголовок PR, автор, дата, ссылка на оригинал  
* Risk Score с breakdown (визуальный gauge или progress bar)  
* Список всех находок: файл, строка, тип уязвимости, CWE, уровень серьёзности, описание, сниппет исправления  
* Mermaid-диаграмма Blast Radius (если применимо)  
* История диалога: все комментарии @secbot и ответы бота в хронологическом порядке  
* Статус: PR прошёл / заблокирован / исправлен

### **5.5 Настройки**

* Подключение репозиториев: форма ввода GitHub/GitLab токена, URL репозитория, настройка вебхука (инструкция \+ автоматическая регистрация)  
* Глобальные настройки: порог Risk Score для блокировки, список глобально игнорируемых паттернов  
* Team-specific исключения: просмотр и ручное управление исключениями, которые накопились через false positive  
* API-ключи: управление ключами LLM (Anthropic / OpenAI), хранятся в зашифрованном виде

### **5.6 Knowledge Base**

* Таблица всех зафиксированных типов уязвимостей с частотой, примерами, ссылками на CWE  
* Поиск по типу, репозиторию, дате  
* Карточка уязвимости: описание, найденные примеры из репозиториев команды, рекомендации по исправлению

### **5.7 Авторизация**

* JWT-авторизация  
* Роли: Admin (полный доступ, настройки), Viewer (только чтение аналитики)

## **6\. API: основные эндпоинты**

* POST /webhooks/github — приём вебхуков GitHub  
* POST /webhooks/gitlab — приём вебхуков GitLab  
* GET /api/repos — список подключённых репозиториев  
* POST /api/repos — подключить репозиторий  
* GET /api/repos/{id}/pulls — список PR с результатами анализа  
* GET /api/pulls/{id} — детали анализа конкретного PR  
* POST /api/repos/{id}/scan — запуск retro-анализа  
* GET /api/stats — общая статистика для дашборда  
* GET /api/knowledge — Knowledge Base  
* POST /api/auth/login — авторизация  
* POST /api/settings — сохранение настроек

---

## **7\. База данных: основные сущности**

**repositories** — подключённые репозитории (id, provider, url, webhook\_secret, settings\_json)

**pull\_requests** — записи о каждом проанализированном PR (id, repo\_id, pr\_number, author, risk\_score, status, created\_at)

**findings** — отдельные находки (id, pr\_id, file\_path, line\_number, type, cwe, severity, description, fix\_snippet)

**llm\_logs** — лог всех запросов/ответов LLM (id, pr\_id, prompt, response, tokens\_used, created\_at)

**dialogs** — сессии диалога (id, pr\_id, messages\_json, updated\_at)

**false\_positives** — накопленные исключения (id, repo\_id, pattern, directory, count, created\_at)

**knowledge\_base** — векторное хранилище уязвимостей (интеграция pgvector или Chroma)

## **8\. Edge-cases и обработка ошибок**

* Пустой PR (только изменения в .md) — бот публикует комментарий "No security-relevant changes detected" и завершает работу без запроса в LLM  
* Очень большой PR (более 500 изменённых строк) — diff разбивается на чанки, каждый анализируется отдельно, результаты объединяются в один итоговый комментарий с пометкой "Analyzed in N parts"  
* LLM не отвечает / таймаут — бот публикует комментарий "Analysis temporarily unavailable, please retry" и логирует ошибку  
* LLM вернул невалидный JSON — повторный запрос с уточнением промпта (до 2 retry), после — логирование и уведомление администратора  
* API провайдера недоступен — задача возвращается в очередь с экспоненциальным backoff (3 попытки)  
* Бинарные файлы в diff — автоматически пропускаются

---

## **9\. Безопасность сервиса**

* Все ключи LLM, токены репозиториев и webhook-секреты хранятся в зашифрованном виде (AES-256 или через Vault)  
* Diff с секретами анализируется локально (TruffleHog/Gitleaks) до отправки во внешний LLM API  
* Верификация подписи каждого входящего вебхука  
* HTTPS everywhere, SSL-сертификаты  
* Rate limiting на webhook-эндпоинтах  
* Изоляция воркеров Celery

## **10\. Сценарии демонстрации (для хакатона)**

**Сценарий 1 — Базовое ревью:** создать PR с намеренно уязвимым кодом (SQL-инъекция \+ hardcoded API key). Показать, как через 10–15 секунд появляются inline-комментарии с Risk Score 85, кнопка merge заблокирована.

**Сценарий 2 — Диалог:** ответить боту @secbot why is this SQL injection?, показать как бот объясняет механизм и показывает PoC curl-запрос.

**Сценарий 3 — Автофикс:** показать автоматически созданный PR, который переносит секрет в .env.

**Сценарий 4 — Retro-анализ:** запустить @secbot scan full или кнопку в UI на реальном репозитории, показать Summary Report с найденными проблемами.

**Сценарий 5 — Дашборд:** открыть веб\-панель, показать статистику, Blast Radius диаграмму, Knowledge Base.
