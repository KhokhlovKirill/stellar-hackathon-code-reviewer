# 01 — Разбор задачи и стратегия набора баллов

## 1. Суть кейса (из task.md + слайдов)

Требуется production-микросервис («бот»), который выступает **отдельным сервисным
аккаунтом-ревьюером** в системе контроля версий (GitHub / GitLab / Bitbucket) и
автоматизирует первый проход security-ревью, чтобы:

- разгрузить узкое горло: очевидное ловит бот за один проход, тимлид смотрит финально;
- не пропускать в основную ветку SQL-инъекции, XSS, сырые запросы, захардкоженные
  секреты, `.env` с секретами, небезопасные/малварные библиотеки;
- экономить деньги на LLM и время: анализируется **только diff**, а не весь репозиторий
  (90% файлов в PR не меняется);
- оставлять подробные построчные комментарии прямо под кодом (как inline-комментарии в
  Bitbucket/GitHub/GitLab) с указанием проблемной строки, сути уязвимости и совета;
- иметь право на **автоматический decline / блокировку merge** при очевидной критичной
  уязвимости (финальный аппрув всё равно за тимлидом);
- вести **полное логирование и аналитику** (что ушло в LLM, что в VCS API, как ведёт
  себя бот) — чтобы доказуемо оценивать корректность работы;
- по возможности отвечать пользователю в треде комментариев (диалог).

Доп. требования из устной части task.md, которые поднимают решение над baseline:

- Проверка **импортов и зависимостей**: библиотека безопасна? есть ли по ней свежие
  CVE / отозванные версии / malware-хэши в pypi.org / npm registry? если небезопасна —
  **предложить замену** исходя из контекста использования.
- Анти-false-positive: «анализатор должен избегать ложноположительных срабатываний».
- Бот действует от **отдельного сервисного аккаунта**, привязка репозитория — через
  токены доступа в админ-портале.
- Стек: Python (приоритет) / Go / Node, обязательно Webhooks, Docker, REST API, LLM API.
- Промежуточная оценка качества предполагается → нужен воспроизводимый eval-харнесс.
- Единого пула тестовых репозиториев организаторы не дают → **мы создаём собственный
  набор vulnerable/clean фикстур** и демонстрируем на нём метрики (это прямо названо
  организаторами «фичей, а не багом»).

## 2. Официальная шкала оценки

Каждый пункт — 0..3, есть вес `w`. Итог = Σ(score × w). Максимум = 3 × Σw = 3 × 32 = **96**.

| # | Приоритет | Критерий | w | Наш план на 3/3 |
|---|---|---|---|---|
| C1 | 1 | Сервис успешно принимает Webhook о создании PR/MR из репозитория | 6 | Подпись HMAC verified, идемпотентность, 3 провайдера, событие PR opened/updated/reopened |
| C2 | 1 | Сервис извлекает только изменённые строки (diff) и отправляет в LLM | 6 | Diff-only, контекст только вокруг changed-lines, доказательство в аналитике (панель «sent vs full repo») |
| C3 | 1 | Распознаёт базовые уязвимости (SQLi, захардкоженные пароли/токены, XSS) | 6 | Детерминированный слой (Semgrep + secret-scan) даёт near-zero-FP recall + LLM-ансамбль добивает контекстные кейсы |
| C4 | 1 | Бот автоматически оставляет комментарий к PR с проблемной строкой и сутью уязвимости | 6 | Inline-комментарий, привязанный к новой строке diff: severity, CWE, объяснение эксплуатируемости |
| C5 | 2 | ИИ предлагает конкретный сниппет для исправления | 3 | Нативный «suggestion»-блок VCS (one-click apply) + diff-патч |
| C6 | 2 | Бот фильтрует файлы, не требующие проверки (README.md, .gitignore, картинки) | 3 | Path/ext/glob-фильтр + `.aegisignore`, бинарь/генерёнка/вендоринг, лог отфильтрованного |
| C7 | 3 | Пользователь может ответить боту в комментариях, бот поддерживает диалог | 1 | Webhook на reply/comment, контекст треда, ответ in-thread, guard от циклов |
| C8 | 3 | Возможность заблокировать merge при критичной уязвимости | 1 | Failing required status-check / Request changes; override только тимлидом |

**Стратегия:** P1 (вес 6×4=24 пункта веса, 72 из 96 баллов) — закрываем на 3/3 максимально
надёжно через **гибрид детерминированного и LLM-детекта** (детерминированный слой
гарантирует recall по SQLi/secrets/XSS даже если LLM-тир недоступен — это страховка
самого дорогого по весу блока). P2/P3 — закрываем полностью, плюс добавляем
дифференцирующую глубину (supply-chain, аналитический дашборд, доказанный uplift
дообученной модели), которая в рамках критерия «сути уязвимости» и анти-FP поднимает
качество оценки.

## 3. Что значит «3/3» по каждому пункту (acceptance)

- **C1 = 3:** webhook трёх провайдеров принят, подпись проверена, дубликат доставки
  не порождает второй прогон, ack < 1s, событие корректно классифицировано.
- **C2 = 3:** в LLM уходит только unified-diff изменённых hunks + узкий контекст; в
  аналитике видно число изменённых строк vs размер репозитория и сэкономленные токены.
- **C3 = 3:** на golden-set (см. `12-evaluation.md`) recall по SQLi/secret/XSS ≥ 0.9
  при precision ≥ 0.85; детект работает даже при полностью недоступном LLM-тире
  (детерминированный fallback).
- **C4 = 3:** комментарий привязан к конкретной изменённой строке (не к файлу целиком),
  содержит severity, CWE-id, 1 абзац «почему эксплуатируемо именно здесь».
- **C5 = 3:** прикладывается применяемый одним кликом suggestion-блок, синтаксически
  валидный, сохраняющий поведение.
- **C6 = 3:** README/.gitignore/картинки/локфайлы/бинарь/генерёнка не уходят в LLM;
  список отфильтрованного — в summary-комментарии и логе.
- **C7 = 3:** ответ пользователю в том же треде с учётом исходной находки и истории
  реплик; бот не зацикливается и не отвечает другим ботам.
- **C8 = 3:** при Critical-находке (политика настраивается) ставится падающий
  required-check, который блокирует merge до ручного override тимлидом.

## 4. Нефункциональные требования

- **Отказоустойчивость:** SSD с дообученной моделью может быть не примонтирован,
  LM Studio может быть не поднят, OpenRouter может быть недоступен — сервис продолжает
  работать на любом доступном тире и помечает деградацию в комментарии и метриках
  (фактическое состояние среды на момент проектирования: `/Volumes/SSD` не примонтирован,
  LM Studio на :1234 не отвечает — это штатный сценарий, а не блокер).
- **Безопасность:** diff — недоверенный вход (prompt-injection через содержимое PR);
  токены VCS — шифруются at-rest, не логируются; webhook — подпись обязательна.
- **Воспроизводимость:** один `docker compose up`, конфиг декларативный, миграции БД,
  eval перезапускается из репозитория.
- **Экономия:** кэш по (repo, commit, file, hunk-hash); map-reduce для больших PR;
  детерминированный слой отсекает часть кейсов без обращения к LLM.
- **Наблюдаемость:** correlation-id = scan-id сквозь все стадии; каждая LLM/VCS-операция
  залогирована с токенами/латентностью/стоимостью.

## 5. Явные не-цели

- Бот **не** аппрувит PR (финальный аппрув — человек/тимлид). Бот может только
  request-changes / поставить блокирующий чек.
- Бот **не** сканирует весь репозиторий — только diff (это требование, не упрощение).
- Не делаем dynamic analysis / запуск кода из PR (это вектор атаки; sandbox-исполнение —
  вне scope, см. модель угроз в `10-security-and-secrets.md`).
