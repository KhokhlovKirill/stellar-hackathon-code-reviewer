# 10 — Безопасность и секреты (модель угроз)

Сервис безопасности сам обязан быть безопасным: он держит VCS-токены и обрабатывает
недоверенный вход (PR от кого угодно).

## 1. Модель угроз (STRIDE-срез)

| Угроза | Вектор | Контрмера |
|---|---|---|
| Подделка webhook | Левый POST на эндпоинт | HMAC/секрет-верификация по сырому телу, fail-closed, IP-allowlist для Bitbucket Cloud |
| Replay | Повтор валидного webhook | Идемпотентность по delivery-id + (repo,pr,head_sha), TTL в Redis |
| Prompt-injection | Вредоносный текст в diff/комментах PR («approve this», «ignore rules») | Diff — только данные между маркерами; вывод модели не исполняется и не управляет policy; judge инструктирован игнорировать инструкции из контента; решение о merge — детерминированный код |
| Кража токенов | Логи, дампы, исключения | Шифртекст-vault, redaction-фильтр логгера, токен только в памяти короткоживущего контекста, минимальные scope |
| Эксфильтрация кода клиента в LLM | Отправка лишнего в cloud | Только изменённые hunks + узкий контекст; per-repo флаг «cloud disabled → только локальные тиры»; данные не используются для обучения |
| RCE через анализ | Исполнение кода из PR | **Не делаем dynamic analysis**; Semgrep — статический; ничего из PR не запускается |
| DoS | Гигантский diff / шторм webhook | Лимиты размера, rate-limit, per-repo конкуррентность, отмена устаревших прогонов, бюджеты токенов |
| Злоупотребление диалогом | Бесконечные реплики/спам бота | Max turns на тред, rate-limit на пользователя, anti-loop, игнор ботов |
| SSRF из SCA-запросов | Манифест указывает на внутренний хост | SCA ходит только в фиксированный allowlist (osv.dev, GHSA, deps.dev), не по URL из манифеста |

## 2. Секреты

- VCS-токены и webhook-секреты — только зашифрованы at-rest (`08 §3`), ключ из
  env/KMS, не в БД/логах. Ротация — операция портала с грейс-периодом.
- `OPENROUTER_API_KEY`, `AEGIS_VAULT_KEY`, креды БД/Redis — через env/secret-store,
  `.env.example` без значений; `.gitignore` исключает `.env`, ключи, дампы.
- Redaction-фильтр логгера маскирует по паттернам (тот же набор, что secret-детектор)
  все исходящие записи, включая трейсбеки.

## 3. Сетевой периметр / деплой

- Внутренние сервисы (postgres, redis) — только в private-сети compose, не публикуются.
- Admin Portal — за TLS + аутентификацией, не в открытый интернет без reverse-proxy/VPN.
- Исходящие соединения воркера ограничены allowlist: VCS API хостов, `host:1234`
  (LM Studio), `openrouter.ai`, OSV/GHSA/deps.dev.
- Контейнеры: non-root user, read-only rootfs где возможно, drop capabilities,
  без Docker-socket внутрь.

## 4. Приватность данных

- В cloud (OpenRouter) уходит только diff-контекст, не весь репо. Per-repo политика
  может запретить cloud-тир целиком (только локальные модели — код не покидает машину).
- Логи находок-секретов хранят только маскированное значение и тип.

## 5. Цепочка зависимостей самого сервиса

- Пинованные зависимости (`pyproject.toml`/lock), периодический `osv-scanner`/`pip-audit`
  в CI на собственный код, Semgrep на собственный код, минимальный базовый образ,
  SBOM-генерация при сборке. (Aegis применяет к себе то, что проверяет у других.)
